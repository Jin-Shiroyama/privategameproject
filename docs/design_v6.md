# 放置ゲー設計メモ v6

v5からの変更：共通ゲート廃止と有効値上限の経緯／4段階の実装区分／保護中の持続カウンタ／常駐型の時間・保存方針／fact単位の開示と知識の時間性／認知時の第三者反応・原子性・複数役割評価／solo相性の最小定義／人口・履歴・NSFW規約の整理。

改訂根拠：v5元本、「v6反映リスト」、同追補、および連携されたレビュー往復。追補による訂正を先行リストより優先する。追加方式は本文の関連節へ統合し、表出保護など未採用の選択肢は未決として残した。

**文書内の確度**：合意済みの方針を「確定」、実装に向けて今回具体化した方式を「実装案」、数値・イベントの具体内容を「検証用案」として区別する。コードや実行済みの仕様ではない。数値例をバランス調整の確定値として扱わない。「未決・候補」は採用を確定していない事項。追補の導出ビュー・バインディング・再開処理の具体形は、整合性を確認した実装案として記載する。

## 改訂上の決定

- 「他人のまま恋人」は、面識があっても友情関係を経ずに恋人になれるという意味。
- 好感度はシステム内部の進行値。各感情の共通の前提にはしない。
- expressedは意思決定・描写の材料であり、必ず態度に出るという意味ではない。
- スキルと状態は増減補正・変化禁止・有効値上限を提供できる。
- 保存値と有効値を分離する。上限を解除すると、現在の保存値に応じた有効値へ戻る。
- 初体験は参加者の役割と実際に成立した結果から記録し、繰り返し経験の集計と区別する。
- 日次区切り・cross_party B案は確定済み。
- 恋愛トラックの最小構成は「恋愛関係なし→恋人」。「意識」・片思い・両思いは感情側で表現する。
- 告白の発生は抽選、返答は結果適用前の値による条件判定。拒否後の再告白を許容する。
- 複数交際を表現でき、キャラのスキルで告白・受諾・感情の育ち方を制約する。
- 関係保護はプレイヤーがペア内のトラックごとに設定する。状態遷移の制約と指定関係値の保存値下限を組み合わせ、昇格は許す。
- 完全保護で成立不能なイベントは抽選候補から外し、結果確定時にも禁止遷移を防ぐ。
- 解消されやすさの調整は完全保護とは独立した将来拡張とする。
- アプリ終了・一時停止・スリープ中は世界を止め、停止時間を後から取り戻さない。
- 把握できない停止（スリープ等）は実測経過時間のクランプで扱い、復帰時に最大で上限分だけ進むことを許容する（§8）。
- 第三者反応は事実の発生時ではなく、新たに認知した時点で発火する。
- factは成立結果のうち開示可能な事実から生成する。内部deltaや軸値をfact化しない。1イベントから複数factを生成し、それぞれの開示範囲を決める。
- 出来事の知識・本人の認識状態・世界の実状態を区別する。本人の認識状態は既知factから導出する実装案。
- 最初の動作試作と後段の機能検証を分離し、履歴と知識の記録基盤は最初から残す（§12）。

## 0) ピッチ

- **CUI・チャットベースの放置型 関係性観察ゲーム**。
- 管理メニューで準備→出発後は、**キャラ達の「グループチャット」ログが流れ続ける**のを眺める。
- 主軸は成長ではなく**関係性とその遷移**(トモダチコレクション系譜)。
- 研究目的: LLM組み込みの個人用プロトタイプ。勝敗なし。
- NSFW要素を含む。通常の関係シミュレーションを担うCasterは全員成人。将来のSFW家族イベント用ChildEntityは別系統とし、恋愛・性的要素へ参加させない（§10〜11）。

## 1) 体験の核

1. キャラ同士の会話ログ(チャット風)を眺める
2. 関係の**遷移イベント**(友達→親友、友情関係なしで恋慕、破局と仲直り 等)が起きる瞬間がハイライト
3. 神視点: expressed軸は有効値の帯ラベルで内心を観察し、latent好感度は内部進行値として生ゲージで確認する(§4)

## 2) アーキテクチャ: 2層分離(確定)

- **シミュレーション層**: 数値のみで高速に回る。tick駆動。LLM非依存で単体成立。
- **テキスト化層**: 通常イベントはテンプレート、**重要イベント(関係遷移など)のみLLM生成**。
- 理由: 毎tickのLLM呼び出しは速度・コスト的に破綻するため。

## 3) 関係モデル: 3層分離(確定)

| 層 | 内容 | 例 |
|---|---|---|
| **solo**(単体属性) | 性格・価値観・気質。delta計算の入力 | 社交性、価値観タグ |
| **directed**(A→B) | 主観評価。**数値軸は全てここ**。A→BとB→Aは独立 | §4の軸一覧 |
| **pair**(A-B) | 客観的な関係。**トラック(離散状態)+固定タグ+共有履歴** | §6 |

- 非対称性(片思い・一方的敵意)はdirected層で表現。**片思いはラベルではなく導出状況**(A→B恋愛度が高くB→Aが低い、という状態から導かれる)。恋人関係の成立条件は双方の値などから判定するが、片側の恋慕や告白の発生には双方向の高値を一律に要求しない。

## 4) 属性軸: 定義データ化+role分離(確定)

軸は定義データで管理し、シミュレーション層とLLM層の共通単一ソースとする。v3で**role**を追加:

- **expressed(表出軸)**: キャラの意思決定・言動・LLMプロンプトの材料。有効値を帯(bands)+hintへ変換する。態度に必ず出ることは意味せず、感情を隠す言動も可能。
- **latent(潜在値)**: システム内部の進行値。**LLMプロンプト組み立てから除外**。イベント・遷移・個別ルールの条件が参照し、キャラの感情として直接解釈しない。帯定義不要。

### 軸一覧(確定)

| 軸 | role | 意味 |
|---|---|---|
| 好感度 | **latent** | 感情そのものではなく、蓄積してイベントや状態遷移のきっかけになる内部進行値 |
| 信頼度 | expressed | 能力・誠実さへの期待。好意系とは独立 |
| 友情度 | expressed | 友情観点の言動に反映 |
| 愛情度 | expressed | 親愛。家族愛・隣人愛を含む |
| 恋愛度 | expressed | 文字通りの恋愛的感情 |
| 性愛度 | expressed | 性的観点の好感(帯・hintはNSFWパック側で定義) |

**確定原則：各感情は独立して保持し、別の感情や好感度を共通の必須前提にしない。** 依存させる場合は個別のイベント・スキル・状態のルールとして明示する。他軸の参照自体は禁止しない。例えば「信頼があると告白が選ばれやすい」は可能だが、「友情がなければ恋愛度は上がらない」という共通制約にはしない。

### 保存値と有効値（要件確定・実装は第④段階）

要件の出所は「スキル保有中は低く扱い、失うと元の値が表に出る」「状態による上限ロックを表現したい」というユーザー要望。保存値・有効値を分ける方式は、その実現方法として了承された。具体的なスキルや状態のコンテンツは未定であり、最初の動作試作にはcapを実装しない。初期は有効値＝保存値として条件参照の窓口を用意する。「一途」の増減倍率はcapの具体例には数えない。

- `stored_value`：イベントの増減を蓄積する保存値。軸固有の数値範囲内に収める。§17の関係保護中は、対象値を指定下限以上に保つ。
- `effective_value`：現在の状態・有効なスキルの制約を反映し、実際に使用する値。
- 意思決定、通常のイベント条件・遷移条件、expressedの帯ラベルには有効値を使う。
- 上限中も保存値は保持する。蓄積を止めたい場合は別途「上昇禁止」を組み合わせる。
- 保存値80、上限30なら有効値30。解除後は有効値80。制限中に保存値が増減した場合、解除後はその時点の保存値に従う。
- 好感度をプレイヤーに示す生ゲージは保存値とする。制約が作用する場合は有効値・制約中の表示を併記して誤解を避ける（表示詳細は実装案）。
- `latent`という軸の役割と、expressed軸の保存値が上限で抑制されることは別概念。

### 定義データ例

```yaml
attribute:
  id: trust
  layer: directed          # solo | directed | pair
  role: expressed          # expressed | latent
  range: [-100, 100]
  negative:
    meaningful: true       # 軸ごとに負数の意味有無を宣言
    semantics: "能動的な不信。裏切りを警戒し情報を隠す"
  bands:                   # LLMには生数値でなく帯+hintで渡す
    - { min: 70,  label: "深く信頼", hint: "弱みを見せる。判断を委ねる" }
    - { min: 20,  label: "信頼",     hint: "頼み事を受ける" }
    - { min: -20, label: "中立",     hint: "距離を保つ" }
    - { min: -100,label: "不信",     hint: "発言を疑う。皮肉が混じる" }
  description: "相手の能力と誠実さへの期待。好意とは独立(嫌いだが信頼する、はあり得る)"
```

- 生数値をLLMに直接渡さない。帯ラベル+hintに変換して渡す。descriptionが軸間混同を防ぐ。
- **latentの可視性(確定)**: キャラ(LLM)には完全に隠す。プレイヤー(神視点)には管理画面で生ゲージ表示。可視性の境界は「LLMプロンプト組み立て」の一点に集約される。

## 5) 関係ルールとスキル

### 効果の種類（確定）

| 種類 | 対象 | 例 |
|---|---|---|
| 増減量補正 | イベントが作ったdelta候補 | 正の恋愛deltaを0.5倍、負の信頼deltaを0.2倍 |
| 変化禁止・ゲート | 補正後のdelta | 条件中は上昇禁止。指定しない限り下降は禁止しない |
| 有効値上限 | 現在の保存値から求める有効値 | 状態中は恋愛度を最大30として扱う |
| イベント条件追加 | 候補選定・返答などの判定 | 特定スキルが再告白に状況改善を要求する |
| 関係保護（プレイヤー設定） | 遷移と対象の保存値 | 解消禁止、降格禁止または状態下限、指定値の下限保証。§17 |
| 解消されやすさ（将来拡張） | 解消の条件・必要期間など | 完全保護とは独立して調整する |

- スキルと状態は同じ補正・制約の仕組みを利用する。状態をすべてスキル化する必要はない。
- `RelationshipPolicy`は適用対象のルールを集めて評価する。個別ルールは定義データ化し、§11の不変条件を除き切替可能。
- v3の「恋愛上昇には好感度30以上」という全体ゲートは廃止。必要なキャラや状態に限定した個別ルールとして定義できる。
- 改訂理由：solo相性を起点に恋慕イベントが成立しても、共通の好感度ゲートが恋愛deltaを消してしまう矛盾があったため。旧来の共通ゲートを置く合意を見直し、各感情の独立性と個別条件へ転換した。
- スキルによる加算で禁止が復活しないように、増減量の補正後、最後に変化禁止を適用する。

### スキル定義と保有実体（確定）

| 項目 | 定義する内容 |
|---|---|
| 獲得方法 | 初期付与／経験条件／イベント結果 |
| 保持・喪失 | 不変／条件で喪失／一時無効化 |
| 適用対象 | 全相手／指定相手 |
| 効果 | 増減補正／変化禁止／有効値上限／イベント追加条件など |

4項目は独立し、「経験で習得し、喪失し得て、特定の相手だけに効く」スキルも表現できる。

- `SkillDefinition`：ID、版、獲得・喪失・有効化条件、効果を持つ。
- `SkillInstance`：保有者、定義参照、必要なら相手ID、獲得イベント、現在の有効状態を持つ。
- 喪失と無効化は分ける。喪失は保有を終了し、無効化は保有したまま効果を停止する。
- 同じ定義でも相手限定の実体を分けられる。A→B向けの効果をB→Aへ自動適用しない。

### 合成・条件評価（実装案）

- 増減量補正はまず倍率のみを実装し、該当倍率を乗算する。増加用／減少用を分ける。加算や符号反転は必要時に拡張する。
- 変化禁止は一つでも該当すれば対象方向をブロックする。
- 上限が複数あれば最小を採用し、`effective = min(stored, active_caps, axis_max)`とする。保存値の軸範囲は別途保証する。
- 上限の適用条件は状態・保有スキル・対象相手などから決める。自分自身が算出中の有効値を条件にして循環させない。
- 通常の条件は有効値を参照する。保存値を直接参照する特殊ルールを導入する際は参照元と意図を明記する。
- 上限30なのに解除条件が有効値60以上、という行き詰まりを避ける。解除は別のイベントや経験条件などで成立させる。

### ルール変更時のデータ扱い（確定）

以前却下した方式B（生値＋実効値ビュー）は、ゲートルール無効化で隠れ値が突然露出するという、ルール運用上の副作用を避けるために却下した。今回のcapでは、スキル喪失等で現在の保存値が表に出ること自体がゲーム内表現の要件である。同じ計算構造でも目的が異なるため、次の役割分担とする。

- 増減補正・ゲートのルール有効／無効：方式A（前向きのみ）。抑止した過去deltaを復元しない。
- スキル・状態が提供するcap：意図された有効値制約。追加・解除時に有効値を再計算し、抑止された過去deltaは復元しない。

- 通常のルール変更では保存済みの値を直接書き換えない。増減補正は以後のdeltaに作用する。例外として、プレイヤーの関係保護による下限保証は、設定時に下限未満の保存値を引き上げる（§17）。
- 上限制約の追加・解除は、現在の有効値を再計算する。これを過去deltaの再適用とは扱わない。
- イベント履歴に候補delta、補正後delta、適用delta、保存値／有効値の前後、作用したルールIDと版を記録する。
- 遡及リプレイはMVP外。
- v4までの「ピン留め＝負delta・降格持続の倍率補正」は、§17の明示的な関係保護へ置き換える。表示上のピン留めとは区別する。

## 6) 関係の状態機械

### トラック並立・面識・固定タグ

- **面識（分離確定）**：出会いの成立結果・共有履歴で管理。片側だけ知っている状況は必要になった時点で拡張する。
- **友情トラック（分離確定）**：初期は「友情関係なし」。友達→親友などを独立に遷移させる。負側「険悪」は拡張候補。
- **恋愛トラック**：恋人など、成立している関係を管理する。
- **固定タグ**：幼馴染・師弟・血縁など。通常のトラック遷移とは別に管理する。

面識があることと友達であることは別。友情関係なしのまま恋人になれる。片思いはdirected値から導出し、pairの状態として重複保持しない。

**恋愛トラックの最小構成は「恋愛関係なし→恋人」で確定。** 「意識」は個人の内心を意味するため、独立したpair状態にしない。両思いでも自動で恋人にはならず、交際成立イベントを必要とする。両思いという数値上の状況から、本人たちが相手の気持ちを知っているとは推定しない。本人の知識・認識は§19に従い、pairの実状態とは別に扱う。

複数のペアで恋人状態を同時に保持できる。交際の制約は§18のスキルで個別に指定する。友情の具体的な段階・閾値は検討対象であり、「他人→友達→親友」という議論中の仮定をそのまま確定仕様にはしない。

### 遷移方式（既存方針を維持）

- 昇格条件を満たしただけでは即時変更しない。対応イベントが候補になり、成立した結果によって遷移する。
- イベントを起こす条件と、成功・失敗および遷移成立の条件は別々に持つ。
- 降格は低値が一定ゲーム内日数持続したら「揺らぎ」に入り、さらに持続するか決定的な負イベントで確定する。
- 揺らぎ期間には仲直りイベントを候補にできる。中間状態を明示状態で持つか付随情報で持つかは実装案の段階。
- 保護中の禁止遷移は必要期間の延長で代用せず、明示的に阻止する。解消されやすさの時間補正などは将来拡張。
- 閾値回復・仲直り成立時のカウンタリセットを基本案とする。具体日数・閾値は調整対象。
- 降格もイベント結果として記録する。決定的イベントも§17の関係保護を迂回しない。

### 友情関係なしで恋慕するイベント（確定）

- 発生条件は個別イベントが定義する。好感度または§21のsolo相性などを利用でき、友情状態を共通前提にしない。
- 作用先は該当方向の恋愛度。好感度不足という共通ゲートで後から拒否しない。
- そのキャラに有効な個別スキルや上限は通常どおり適用する。
- 恋慕したことと恋人関係の成立は別の結果。恋愛度の増加だけで恋人ラベルを付与しない。

## 7) イベント処理順

以下の責務分離・順序は確定。再評価回数や記録キーなどの詳細は実装案。

1. **開始時点の情報を取得**：状態、スキル、保存値、有効値、履歴から候補を作る。スキルの追加条件と保護を評価し、成立不能な専用イベントを候補から除外してから抽選する。発生条件と結果の分岐条件を区別する。
2. **結果候補を作成**：参加者の役割、成否、delta候補、状態・スキルへの変更要求を作る。告白の受諾／拒否は開始時点の値・状態・スキルで決め、返答の追加抽選は行わない。この時点では永続化しない。
3. **増減を補正**：開始時点で有効なスキル・ルール・保護を適用。補正後、変化禁止を適用する。
4. **値を仮更新**：保存値を軸範囲と有効な保護下限の範囲内で更新し、現在の制約で有効値を求める。今回の結果に対応する状態遷移を評価する。告白の受諾条件を成功時delta適用後の値で再判定しない。
5. **状態・スキルを更新**：結果確定前にも保護による禁止遷移を検証し、許容される変更と経験に応じた獲得・喪失を反映する。新しい制約で有効値を再計算する。
6. **一括確定**：値、状態、スキル、成立結果、初体験、経験集計、履歴を同じ更新単位で保存する。EventResultの観測者候補、成立結果から生成するfactとfactごとの開示範囲、認知・反応の未処理作業も同じ確定単位に含める（§19〜20）。初体験・経験集計など未実装の機能は§12の段階に従い、後から参照する成立結果を先に保存する。
   - 認知・反応機構の実装後は、確定した元イベントを受けて認知作業を処理する。知識参照の追加、反応delta・適用済みキー・即時ログ・後続候補・作業完了を、§20の一つの更新単位で確定する。これは新しい抽選イベントの即時連鎖とは区別する。
7. **テキスト化**：確定した結果と値の帯を渡す。キャラ発話用には§19の知識境界も適用し、神視点用の世界状態をそのまま全員の既知情報にしない。LLMが成功を失敗に変えたり、未成立の体験を創作したりしないように結果を明示する。

### 更新中の循環を防ぐ実装案

- ステップ5のスキル習得判定は、今回成立する経験を含めた仮集計を参照できる。
- 今回獲得したスキルのdelta補正は次イベントから有効。新しい上限は今回の最終有効値に適用する。
- 状態変更後の有効値を理由に同じイベントを無制限に再実行しない。一つのイベント内で遷移の確定は各トラック最大一回を基本案とする。
- 条件充足で他イベントが候補になっても、自動で連鎖実行せず次回の選定対象とする。
- 同時刻のイベントは安定した順序で逐次確定する。初回が競合した場合は確定順で一件のみ作成する。
- 初体験生成を含め、一部だけ保存された状態を残さない。再処理時はイベント実体IDで二重適用を防ぐ。

### 検証用の上限制約例

ある状態または相手限定スキルが、A→Bの恋愛度に`effective_cap: 30`を提供する。

| 操作 | 保存値 | 上限 | 有効値 |
|---|---:|---:|---:|
| 初期 | 80 | なし | 80 |
| 制限開始 | 80 | 30 | 30 |
| 制限中に+10、蓄積を許可 | 90 | 30 | 30 |
| 制限解除 | 90 | なし | 90 |

蓄積も止める場合は`block_increase`を併用する。この場合、+10はブロックされ、解除後は80となる。上限は値を切り捨てる処理ではない。

## 8) 時間・保存設計

### 進行方針（確定）

- 常駐型。アプリを閉じれば世界も止まる。オフライン差分計算は実装しない。
- 一時停止・PCスリープ中も停止し、その時間を再開時に取り戻さない。再開時は実時間の計測基準を置き直し、停止分を大量tickへ変換しない。
- 進行速度設定は実時間に対するゲーム内時間の進む速さのみを変える。1ゲーム日が実時間何分に相当するかなどの具体値は調整対象。
- **実測経過時間のクランプ（第①段階で採用・確定）**：常駐ループは毎回 `elapsed = min(実測経過, 上限)` の分だけゲーム内時間を進める。スリープ・デバッガ停止・高負荷など、把握できない停止や遅延を同じ一つの規則で扱う。次の挙動を仕様上の妥協として許容する。
  - 復帰・再開時には、最大で上限分だけゲームが進む（停止時間そのものは取り戻さない）。
  - 上限を超える高負荷が続く間は、実時間に対してゲームの進行が遅れる。
  - 上限値は定義データ側の設定とし、コードに埋め込まない。
  - 明示的な一時停止・終了後の再起動では、従来どおり実時間の計測基準を置き直す。クランプはこれを代替せず、把握できている停止時間を後から進める必要もない。

- 疑似時間tick。**deltaをtickに紐付けない**(イベント単位/経過ゲーム内時間単位で定義)。tickは純粋なスケジューラ。
- 区切り: **日次で確定**(遷移の節目・要約単位)。日次評価は専用の日次処理イベントとして履歴化する。

### 保存方針（確定）

- 終了時保存＋定期自動保存のスナップショット方式。正常終了時の保存だけに依存しない。異常終了時は最後に成功した保存まで戻り得る。
- 世界状態・ゲーム内時刻・乱数生成器の状態・進行中／未処理の処理・適用済みIDを保存する。最初のseedだけでは途中再開の再現性を保証しない。
- 未処理認知／反応、必要な後続イベント候補、クールダウンや持続カウンタも保存対象。定義データの版と安定した確定順も再開時に維持する（具体形式は実装案）。
- 同じ保存先ファイルシステムの一時ファイルへ書込み完了後、アトミックに差し替える。書込み途中のファイルで既存セーブを上書きしない。強制電断への耐久性まで保証する場合のflush／同期方法は保存実装時に確認する。
- スナップショットは§7・§20の確定単位の途中を採取しない。保存方式と論理的な一括確定の両方を守る。

### LLM接続時の未決事項

LLM応答待ち中にシミュレーションを進めるかは未決。シミュレーションを継続してテキスト生成を非同期化する案を候補として残す。その場合は、生成入力をイベント確定時点に固定し、表示順・遅延・失敗時のテンプレート代替を決める。進行速度を設定項目にしただけで、これらの設計が不要になるわけではない。

## 10) NSFW方針(確定)

- **前提：恋愛・NSFW系イベントの参加者は全員成人Caster。ChildEntityが絡む恋愛・性的要素は扱わない**（§11の不変条件）。
- **コンテンツパック分離**: コアエンジン(関係・イベント・属性の仕組み)はSFWで完結。NSFWは差し替え可能なコンテンツパックとして分離 — 明示的なイベント定義・性愛度の帯/hint・生成プロンプトの中身はパック側に置く。
- 実行時のテキスト生成は組み込みLLM(ローカルモデル等)が担当。パック側で強度レベル(示唆→暗転→明示)を段階化。
- NSFWイベントも§7パイプラインと§5の個別ルールを通す。全イベントへ一律の双方向閾値を課さず、対象イベントごとに「参加者の区分」「行動の発生条件」「受諾・拒否条件」を分離定義する。
- **性愛度が高いことを、参加の受け入れと同一視しない。** 複数者が関わる行動では、関与者ごとの受諾条件・拒否条件を評価し、必要な受諾が成立しない結果を受諾成立として扱わない。返答は告白と同様に適用前情報の条件判定で決める。具体閾値や追加条件はパック側の規約・定義に置く。
- 妊娠・出産イベントは**SFWコンテンツとして本体側**に置き、発生条件のみNSFWパックから参照される構成。

## 11) 子ども(ChildEntity)の安全設計(確定・不変条件)

「子どもを通常の状態遷移から完全独立させる」を運用ルールでなく**構造的保証**にする。

### ライフサイクル

1. **妊娠・赤ん坊**: 母ユニットの属性+数量として存在(エンティティ化しない)。父親との関係はpair層の固定タグ`血縁`で記録。
2. **子ども**: `Caster`とはスキーマが異なる**`ChildEntity`**。恋愛度・性愛度に相当するフィールドが**型として存在しない**(フラグ方式は確認漏れ1つで破綻するため不採用 — 不正な状態を表現不可能にする)。独自の小サイクル(成長段階、家族イベント登場)を持ち、既存キャラとの関連はsolo属性と固定タグの範囲のみ。
3. **成人**: 成人イベント発火時に**新規Casterを生成**し、ChildEntityは退役(書き換えでなく生成)。引き継ぎはホワイトリスト方式: solo属性(子ども時代に形成された性格)と固定タグ(血縁・幼馴染)と、§15の変換層で生成した来歴。**全directed軸は必ず初期値から開始**し、子ども時代のデータからシードしない。幼馴染→成人後の恋愛はタグ経由でイベントが扱える。
4. 成長遷移の実装方式は後回し(時限式にはしない)。「成人イベントという単一の門を通らない限りCasterになれない」構造のみ必須。

### ハードコード不変条件(§5の可変ルールの枠外)

- NSFWタグ付きイベントの参加者にChildEntityが混入したらエンジンレベルで拒否。
- NSFW系のLLMプロンプト組み立てにChildEntityのデータを渡さない。
- NSFWタグ付きfactをChildEntityの知識セットに入れない。目撃・伝聞・再開処理のすべてで適用する。
- 恋愛・性愛系ReactionRuleでは、観測者と作用対象も成人Casterに限定する。フィールドが存在しないことに頼って適用可否を決めず、役割の型・ルール区分を検証して不正な割当を拒否する。
- 設定でオフ不可・コンテンツパックから上書き不可の層に置く。可変にする理由がなく、可変であること自体がリスク。

## 14) 初体験・経験・成立結果

### 方針（確定）

- 初体験は数値ではなく記録オブジェクト。誰の何の初回か、誰と経験したかを保持する。
- 単なるイベントタグではなく、実際に成立した結果と参加者の役割から自動検出する。
- 告白した人／された人、成功／失敗を区別する。告白成立と恋人関係成立を同じ事実にしない。
- 初回記録と繰り返し経験の集計は別。冒険を3回共有した等の条件は集計で判定する。
- 初体験は通常イベントで上書きしない。記録と集計をスキル習得、遷移条件、LLM文脈へ接続する。

### データ構造（実装案）

| データ | 主な内容 |
|---|---|
| EventResult | イベント実体ID、結果種別、成否、参加者IDと役割、ゲーム内日時、確定順、observed_by（観測者候補） |
| Fact / Knowledge | 成立結果からの開示可能な事実と、キャラごとの知識参照。結果・経験記録とは別の責務。§19 |
| ExperienceCategory | カテゴリID、adult/child、検出する結果と役割、相手必須か、LLM提供可否、パック |
| FirstExperience | 所有者ID、カテゴリID、関与者IDと役割、元結果ID、ゲーム内日時 |
| ExperienceAggregate | 所有者、経験種別、必要なら相手、成立回数など |

- 初回の一意性は原則「所有者＋domain＋カテゴリ」。相手IDを一意性へ含めると「人生初」ではなく「相手ごとの初回」になるので、必要なら別カテゴリとして明示する。
- FirstExperienceには他の参加者を役割付きで記録できる。体験の主体をイベント参加者全員と決めつけない。
- 「初告白した」は`confession_made`のinitiator、「初告白された」は同じ結果のrecipientから別々に作成する案。
- 「初めての恋人」は`relationship_established: lovers`の成立結果から双方に生成する案。
- 恋愛deltaが増えただけで「初恋」を自動生成しない。恋慕が成立した結果の定義を用意する。ただし、内部の経験結果として記録されたことと、他者へ開示可能なfactになることは別。内面だけの結果を自動的に知識化しない（§19）。
- LLM提供可否はカテゴリごとに指定する。latent好感度の非提供とは別の設定。
- 経験カテゴリの全一覧と閾値はコンテンツ設計として後日追加する。

## 15) 子ども時代の経験と成人時の変換層

会話で了承された基本方針を統合する。§11のCaster／ChildEntity分離を維持し、MVP外として接続点を予約する。

- 経験カテゴリを`domain: adult | child`で分離する。子ども側は友達・冒険など独自カテゴリを持つ。
- 子ども時代の記録を大人カテゴリの初回記録として移さない。「成人後の初回」を表すカテゴリであることを文言にも反映する。
- 成人は新Caster生成＋ConversionLayer適用。旧ChildEntityの記録は成人側のdirected値へ変換しない。
- 変換は宣言的マッピングで行い、出力型を`solo_delta / pair_tag / biography`に限定する。
- solo属性・タグは具体的な出力先もホワイトリスト化する。型名だけで任意の効果が安全になるとは見なさない。
- biographyは子ども時代の事実を来歴として保持する。通常の人物説明に利用し、§11のNSFWプロンプト分離を維持する。
- 共有回数は§14の集計から参照する。初回記録だけで「冒険3回」を判定しない。
- 成人時の旧ID→新ID対応を保持し、許可した関係参照だけを再リンクする。過去のイベントの当時のIDは書き換えない（実装案）。
- 相手の成人も必要なペアタグ変換は相手の成人まで保留し、双方が成人した段階で一度だけ確定する。
- 血縁の記録対象や、新Casterへの再リンクに必要な人物識別の詳細は、ChildEntity実装時に具体化する。

## 16) 遷移イベントの整理案と告白の確定仕様

以下の一覧は整理案。告白の挙動は後述の確定仕様を優先する。条件の具体数値やイベント全体のMVP採否を、この表だけで確定しない。

| イベント | 発生条件の例 | 実際に成立する結果 | 関係への作用 |
|---|---|---|---|
| 出会い | 同一イベントで初めて交流 | 面識の成立 | 面識記録を作る。友情状態は自動変更しない |
| 意気投合 | 双方の友情有効値・共有経験 | 友達関係の成立 | 友情関係なし→友達 |
| ときめき | 好感度またはsolo相性など | 片側の恋慕 | 該当方向の恋愛delta。恋人状態にはしない |
| 告白 | 告白する側の有効値・性格など | 告白した／された、返答、成功時の関係成立 | 相手側の条件も評価し、成立時だけ恋人へ |
| ケンカ | 性格や直近の関係変化 | 対立 | 負delta。直ちに関係解消するとは限らない |
| 仲直り | 揺らぎ中など | 和解 | 回復deltaと降格カウンタのリセット |
| 関係の悪化 | 日次持続条件または決定的結果 | 揺らぎ開始／降格 | 対応トラックを変更 |
| 遠征・遭遇・キャンプ | 既存イベント枠組み | 参加・共同作業など | delta、共有経験の集計 |

- 発生条件、結果の分岐条件、成立後の遷移条件を分離する。同じ条件を複数箇所に無関係に複製しない。
- 告白の返答は条件判定で受諾／拒否を決める。発生の抽選と成功率の抽選を重ねない。
- クールダウンはイベント定義で指定する実装案。告白は「実行者→相手」、共有イベントは「ペア」など、適用範囲も明示する。
- 初体験用のタグを列挙する方式から、成立結果をカテゴリ定義が検出する方式に変更する。

### 告白・再告白（確定）

- 告白する側の感情・状態・スキル条件を満たすと抽選候補になる。
- 受け手→告白者の恋愛有効値を基本材料とし、受け手のスキル・状態・経験の個別条件を含めて返答を決める。
- 判定は結果適用前の値を使用する。成功に伴う恋愛deltaを成功判定の根拠にしない。
- 友情・愛情・内部好感度は全員共通の必須前提にしない。
- 受諾時のみ恋人へ遷移し、告白経験と関係成立を別々の結果として記録する。
- 拒否時は恋愛関係なしを維持し、恋愛度を自動的にゼロにしない。拒否の影響はスキルの増減補正を受ける。
- クールダウン終了後、告白者の条件が続いていれば再告白の候補に戻れる。状況改善は共通の必須条件にしない。
- スキルにより再告白の追加条件を設けられるようにする。具体的な改善条件の実装は後回しでよい。
- 初回記録は保持し、再告白は通常履歴と経験回数へ追加する。
- 再告白で条件が同じなら返答も同じ。返答のための追加抽選は行わない。

### スキルによるイベント追加条件（仕組みの方針確定）

- 共通条件と、適用されるスキルの追加条件を両方満たした場合に候補／受諾を許可する。
- 行動の制約を感情値の上限で代用しない。恋愛感情が強くても、追加条件を満たすまで行動しないキャラを表現できる。
- 「前回拒否以降の親密な交流」「共同作業の経験」など、本人が経験した出来事を改善条件に使う案。相手の内心を無条件に既知として扱わない。
- 将来の数値比較用に、前回告白の結果と当時の関係値を参照できるよう履歴の接続点を設ける。具体的なスキルと条件は後日定義する。

## 17) ペア・トラック別の関係保護（確定）

### 目的と適用単位

- プレイヤーが特定ペア内のトラックごとに設定する関係保護。キャラのスキル、表示上のお気に入り登録とは別。
- 「状態遷移の保護」「指定関係値の保存値下限」「成立不能なイベントの候補除外」を組み合わせる。
- 昇格は許可するが、通常の成立条件やイベントを省略して自動昇格させない。
- 完全保護は解消確率0や必要期間の延長で代用せず、禁止された遷移を明示的に成立不能にする。
- 決定的なイベントでも保護を迂回しない。

### 遷移制約

| 指定 | 挙動 |
|---|---|
| 解消禁止 | 関係が残る降格は許可し、解消は禁止 |
| 指定状態を下限 | 下限を割らない範囲で降格を許可 |
| 降格・解消禁止 | 昇格後も、その状態からの降格・解消を禁止 |

- 固定の状態下限と、昇格後にも降格しない方式は区別する。
- トラックごとに異なる指定ができる。友情は降格あり、恋愛は昇格のみ、といった組合せを表現する。
- 遷移の意味を定義データに明記し、状態名の並び順だけで昇格／降格／解消を推定しない（実装案）。
- どの状態段階・どの数値を下限にするかは別途設定する。友情の段階・閾値は今回の例では確定しない。

### 関係値の下限

- 保護対象の軸と方向(A→B、B→A)を明示する。恋愛の保護から友情・信頼まで自動的に底上げしない。
- 下限は有効値だけでなく保存値に適用する。保護中の下降を裏で蓄積しない。
- 設定時点ですでに保存値が下限未満なら、下限まで引き上げる。
- 保存値更新時は、補正・変化禁止を適用したdeltaに対して最後に保護下限を保証する。上昇は通常どおり許可する。
- 下限を超える下降分は切り捨て、解除後も持ち越さない。解除は過去値への巻戻しではなく、その時点の保存値から通常の変化を再開する。
- 例：80に-30、下限60なら更新後60。解除しても60。設定時40・下限60なら60へ引き上げる。
- 軸の数値範囲外の下限は設定しない。複数の保存値下限を合成するなら最大を採用する（実装案）。
- スキルの有効値上限とは作用先が異なる。保存値下限60・有効値上限30の併用では有効値が60以上になる保証はまだない。数値の併存は可能だが、保護の体験保証は別途定義する。どちらかを暗黙に無効化しない。

### 悪化の持続カウンタ（確定）

- 保護で禁止する遷移のカウンタは、保護開始時にリセットし、保護中は進めない。
- 保護解除後はその時点から改めて悪化の持続を判定する。保護前・保護中の時間を持ち越して解除直後に降格させない。
- 非保護トラック、保護設定で許可している降格のカウンタには干渉しない。
- この待ち直しの保証は持続判定による降格・解消に限る。解除後に新たに起きる決定的イベントを一律にN日待たせるものではない。保護中は決定的イベントでも禁止遷移が成立しない。

### 保護が約束する体験（未決・候補）

遷移禁止と保存値下限だけでは、有効値がcapで低いままの場合に冷たい会話・対立が残る。「形式的に関係だけ残る」を避けるという保護の目的を満たすかは、数値上の併存とは別に判断する。

候補として**表出保護オプション**を残す。プレイヤーが明示指定したペア・方向・軸についてcap効果を無効化する案であり、通常の保護へ自動追加しない。採否・対象範囲・保証する描写を第④段階で決める。capの無効化だけであらゆる不穏な描写が消えるとは保証せず、個別イベント条件との整合も確認する。

### 抽選と結果の整合

- 破局専用など、保護によって成立できないイベントは抽選前に除外し、抽選枠を消費させない。
- ケンカなど複数の効果を持つイベントは、許容される対立・数値変化を残せる。破局結果は成立させない。
- 結果の依存関係を守る。破局を止めた場合は「元恋人化」「破局経験」など、破局成立を前提とする効果も生成しない（実装上の整合要件）。
- 保護で破局が成立しなかったことを、キャラが実際に別れを宣言したという出来事へ自動変換しない。
- LLM・テンプレートには確定した結果だけを渡す。未成立の破局を会話・履歴に作らない。
- 全候補が除外された場合は、イベントなしで時間を進めることを許可し、必ず成立するまで再抽選し続けない（実装案）。
- 設定変更と数値引上げ、下限によるdelta抑止を履歴に残す。設定操作を恋慕や初体験イベントとして扱わない（実装案）。

### 将来拡張：解消されやすさ

- 完全保護とは別の設定として、解消条件の厳しさや悪化の必要持続期間などを調整できるようにする。
- 今すぐの実装は不要。具体的な係数や作用方式は未決。
- 完全保護が有効な場合、解消されやすさの設定に関係なく、禁止された解消は成立しない。

## 18) 複数交際と「一途」スキル（確定）

- 同じキャラが複数ペアで恋人状態を持てる。全体共通の恋人一人制限を設けない。
- 個別スキルで、自発的な告白・受諾・相手に求める条件・感情変化を独立に制御する。
- 一つのスキルに複数の効果をまとめられる。

| 「一途」の効果 | 恋人がいる間の作用 |
|---|---|
| 告白制約 | 現在の恋人以外に告白しない |
| 受諾制約 | 現在の恋人以外からの告白を受け入れない |
| 感情補正 | 現在の恋人以外への正の恋愛deltaに倍率を掛ける |

- 「相手にも恋人が一人だけであることを要求する」は別の特性であり、「一途」には自動で含めない。
- 倍率0なら上昇を止め、0より大きく1未満なら育ちにくくする。具体倍率は調整対象。
- 恋人がいなければ上記の三効果は作用しない。既存の恋愛感情を消す・切り下げる効果は含めない。
- 複数恋人を持つ状態で習得した場合は既存の全交際を維持し、新規の相手との交際を制限する。
- 喪失・無効化時は制約と補正を解除する。過去に抑制した恋愛deltaを復元しない。
- 別ペアの交際成立だけで既存ペアを自動解消しない。既存の恋人側の反応は個別のイベント・特性として定義する。

## 19) 事実・知識・認識状態

### 原則とデータ（基本方針確定・構造は実装案）

関係モデルのsolo／directed／pairとは別に、出来事のfactとキャラによる参照を管理する。知識のための新しい感情軸を作らない。

- **知識の源は成立結果のみ。** delta・軸値の変化はfact化せず、当事者にも相手の数値や本心を自動付与しない。この制限は先行リストにも存在していた。
- ただしEventResultに記録されたすべての結果を自動公開する意味ではない。結果種別ごとのfact生成定義が、開示可能な出来事だけを選ぶ。内面の恋慕と「好意を伝えた」は区別する。
- **1イベント→複数fact**を許す。告白の発言、返答、交際成立は別factとなり得て、各factのaudienceを独立に決める。
- 同一の出来事に由来する同一factは共有し、知識はキャラ×factの参照として持つ。別の日の再告白・再交際は別fact。伝聞するたびに元の出来事のfactを複製しない。

| データ | 主な項目・意味 |
|---|---|
| Fact | id、source_result、kind、subjectsと役割、game_date、確定順、必要ならtrackとstate_after、内容区分、初期開示定義・audience |
| Knowledge | owner、fact_id、via（participant／witnessed／told）、acquired_at、取得順、told時のlearned_from |
| 認識状態ビュー | owner・pair・trackをキーとして既知の関係変化factから導出。独立した正本として保存しない |

### 開示と認知の経路

- `observed_by`はイベントに同席した非参加者の**観測者候補プール**。候補にいるだけで全結果を知るわけではない。
- fact生成段で、参加者と候補プール、およびfactごとの開示条件からaudienceを確定する。当事者であっても、当該factを知り得る範囲だけ付与する。
- 最初の簡略実装では`public`を「その場の参加者・同席候補へ公開」、`participants_only`を「当事者内で公開」とできる。publicは全世界のキャラへの配信ではない。必要なら明示受領者を指定し、小声の返答などを一部へ限定する。
- audienceは**当該発生時の直接開示先**。後の伝聞は別の獲得経路として記録する。秘密を他言できるかは話し手側の属性・スキル・イベント条件で制御し、初期audienceを恒久的な伝聞禁止名簿とは扱わない。
- 噂話は、話し手が知るfactから新しさ・重要度・口の堅さ等の条件で選び、聞き手が新規に知った場合だけ反応を発火する。聞き直しで同じ反応を再適用しない。
- 当面、噂は実際の出来事が遅れて伝わるもの。意図的な嘘・伝言の歪みは実装しない。古い事実しか知らないための認識の遅れは表現する。

### 時間的な意味（導出ビューの実装案）

| 参照 | 意味 |
|---|---|
| `knows_event(owner, fact条件)` | 過去の出来事を知っているか |
| `believes_state(owner, pair, track)` | 既知の関係変化から、最後に把握した状態は何か |
| 世界のpair状態 | シミュレーション上の現在の実状態 |

`believes_state`は、そのキャラが現在知っている関係変化factを**発生日時＋同時刻内の確定順**で並べ、state_afterを畳み込んだ最終状態とする。取得日時で上書きしない。同日中の交際・破局を区別できるよう、game_dateの日付だけを順序キーにしない。参照可能なfactがなければ「不明」とし、「恋愛関係なし」と同一視しない。

関係変化factには変更後の状態を明記する。交際成立を知らず破局だけ聞く場合にも、欠けた前段の事実を補作せず最後の既知状態を導ける。導出キャッシュは作ってよいが、factとKnowledgeから再構築できるものにする。

例：BとCが交際し、後に破局したが、Aが交際成立しか知らなければ、Aの最後の認識は「恋人」。これは現在の実状態を確認できた意味ではない。Aが破局を知れば「恋愛関係なし」へ更新し、その後で古い交際成立を知っても認識を恋人へ巻き戻さない。必要な条件では、根拠factの日時も参照する。

告白を受けて得るのは「好意を伝えられた」という出来事の知識であり、相手の現在の恋愛度・本心を読み取る能力ではない。古い出来事の新規認知も反応トリガーにはなるが、現在の認識を条件にするかはReactionRule側で明示する。

### LLMへの接続

- キャラ発話の入力に渡す事実は、そのキャラの知識セット内に限定する。獲得日時と出来事の日時を分け、最近起きたことと最近知ったことを混同しない。
- 世界の正確なpair状態や他人の内面を、キャラの既知情報として漏らさない。神視点の管理表示・説明ログとは用途を分ける。
- キャラ別入力の整理だけで、生成文が知識境界を守ると保証しない。複数キャラを一度に生成するとモデルは全員分の情報を見得るため、プロンプト指示・出力検証、必要に応じたキャラ別生成をLLM接続段で検討する。
- Knowledgeの追加には§11の内容区分・型制約を適用する。

## 20) 認知時の第三者反応（ReactionRule）

### 発火・作用・描写（方針確定）

- 発火点は**初めて事実を認知した時点**。参加・目撃・伝聞を共通の経路で処理する。第三者向けルールは観測者が当該factの当事者ではない等の適用条件を明示する。
- 観測者から見たbeloved／rival等の役割を解決し、条件に合うReactionRuleがdelta候補を作る。作用は通常の§7の補正・変化禁止・値範囲・保護を通し、直接値を書き換えない。
- 交際成立を知った全員が嫉妬する前提にしない。標準形では観測者条件にsolo特性／スキルを含め、祝福・落胆・無反応を別ルールまたは非該当として表す。
- 信頼度は能力・誠実さへの期待。恋敵になったことだけを理由にtrustを下げる共通ルールは置かない。特定の不信傾向や別の出来事を根拠に信頼へ作用させる場合は、意図を個別に定義する。
- 小さな反応も履歴と神視点の値へ反映する。強い反応には**成立時点で短いテンプレートログ**を残し、描写のための抽選を待たない。強度の基準と閾値はルールごとの調整事項。
- 後の相談・落ち込んだ会話・問い詰める行動などは、別イベントの抽選候補に積む。反応から即時に新イベントを連鎖実行しない。
- 後続イベントは元の反応deltaを再適用しない。参照する反応ID／factを持ち、その後続行動自体に独立した効果がある場合だけ、別の成立結果として適用する。

### 役割割当と冪等性（実装案）

- 既定の`binding_policy: all_matches`では、条件に合う役割割当を全列挙し、それぞれ独立に評価・適用する。同じ割当の重複列挙は除く。
- 冪等キーは **(ルールID, fact ID, 観測者ID, 正規化したbinding)**。bindingは役割名とキャラIDの対応を安定した順で表し、辞書の列挙順などに依存させない。ルール版は別に履歴・未処理作業へ固定し、版更新だけで既知factを再発火させない。
- 当事者双方を好きな観測者には2通りの割当が成立し得る。all_matchesでは双方に反応が出ることを仕様として許す。観測者自身も一方の恋人なら、その条件をルールへ明示して反応を分ける。
- `strongest_only`は候補として選択可能な方式とする。導入するルールは強度の決定的な採点式を定義し、同点時は正規化binding順等の安定順で一つ選ぶ。強度の定義なしで「最強」を推定しない。最初はall_matchesのみで実装可能。
- 同一認知に対する条件と役割割当は反応前の共通スナップショットで評価する。一つ目の反応deltaで二つ目の候補条件が変わらないようにする。適用順はルールID・binding等で安定化し、非線形な下限・範囲制約も含め決定的に処理する。
- 複数ルールが一致すれば既定では各ルールを適用する。同時発火させたくない祝福・落胆等は、条件を排他的に定義する。ルールを並べただけで自動的に一つへ絞られるとはしない。

### 原子性と再開（要件確定・確定単位の具体形は実装案）

知識の一意制約だけでは、知識だけ保存されて反応が欠落する事故を防げない。次の形で§7-6の確定機構を再利用する。

1. 元イベント確定時にfactと開示先を保存し、受領者ごとの**未処理認知・反応作業**を同じ更新単位で永続化する。この時点の待機作業は、完了済みKnowledgeとは区別する。
2. 作業を処理し、知識参照の追加、条件に合う全反応のdelta・履歴・適用済みキー、即時ログ、後続候補、作業完了を**一括確定**する。反応なしの場合も知識追加と完了は一括で行う。
3. 再開時は未処理作業から続け、完了済みキーの効果を再適用しない。反応だけ／知識だけの部分保存を残さない。

初期実装では通常の次イベントへ進む前に認知作業を安定した順で処理し、再開時も先に未処理作業を処理する。再開時に評価入力が変わらないよう、元イベント後の状態・処理順・定義版を保持する。反応内部の仮更新は保存対象にせず、未確定なら作業全体を再評価する。

fact生成・作業作成も元イベントID等の安定した識別子で重複を防ぐ。反応による内面delta自体は新しい公開factを生まない。後続行動が成立して初めて、別の開示可能な出来事になり得る。

第①段階は反応未導入のため、fact・開示先・Knowledgeを元イベントと一括記録する。第②段階では上の処理へ移行する。別途の常駐キューサービスや新しい保存システムを必須にはしない。

## 21) 相性関数の最小定義（実装案）

- 相性はsolo属性から導く読み取り専用値。directedの蓄積軸にせず、deltaで直接増減しない。solo属性が変われば相性も変わる。
- 定義は方向付き`compat(A→B)`。初期コンテンツは対称ルールだけでよいが、将来の非対称ルールを表せる形にする。
- `compat(A→B) = clamp(該当affinity_ruleのvalue総和, -100, 100)`。該当なしは0。乱数を使わず、低確率性はイベント抽選側で扱う。
- 同一ルールは1方向の計算につき最大1回。`symmetric: true`なら正順または逆順の条件一致で適用し、両方一致しても同じ方向へ二重加算しない。
- キャッシュするなら入力solo属性が変化した場合と、相性定義を更新した場合に無効化・再計算する。
- latent準拠でLLMプロンプトへ渡さない。神視点の表示は可能。参照先はイベント発生条件・抽選重み・返答判定条件とし、相性を直接のdelta補正倍率にしない。
- 特定相手への感情の動きやすさは、相手限定スキルの倍率等で扱う。相性はsolo由来という境界を維持する。

```yaml
affinity_rules:
  - id: caretaker_pampered
    when: { a_has: 世話好き, b_has: 甘え上手 }
    value: 20
    symmetric: true
  - id: neat_vs_sloppy
    when: { a_has: 潔癖, b_has: ずぼら }
    value: -20
    symmetric: true
```

数値・性格タグは検証用。タグが少なく相性0が多い場合にも好感度経路で恋慕候補になれるが、交流自体が抽選されない問題は残る。好感度経路の存在で飢餓対策が不要になるとはしない。

## 22) 長期運用の方向性と追加検証

### 人口（方向性のみ・具体方式は未決）

活動人数・上限と、追加／入替の扱いを設計する。関係を全組保持する場合、directedはN(N−1)組になり、人数増加で保存量とイベント密度が変わる。新規追加制限や活動メンバーの入替でも成立する。死亡・老化・引退・転出・世代交代は選択肢であり、必須にはしない。成人化と上限が競合する場合の待機・入替、退場者への既存履歴参照は人口実装時に決める。

### 履歴とLLM用記憶（保持原則確定・期間は未決）

| 用途 | 保持するもの |
|---|---|
| 初体験・回数条件・知識の根拠 | 正確な構造化記録、fact、知識参照、経験集計 |
| 調査・再現 | 必要な範囲の詳細履歴、定義版、適用順等 |
| LLMの会話文脈 | 関連する既知factと、用途に応じた文章要約・来歴 |

構造化データを文章要約で置換しない。要約対象は自由文ログ・LLM用記憶とし、要約を経験集計や認識状態の正本にしない。保持期間や削除方針は未決で、削除対象が初体験・知識・未処理作業等から参照されていないか確認して決める。文章を短くすることと、正確な記録の容量管理は別課題として扱う。

### 抽選の飢餓（バランス段の必須検討）

交流が長期間当たらないペアへの補正を検討する。未抽選期間ボーナス等は候補であり、方式・係数は未決。補正で成立条件や保護による候補除外を突破しない。相性・好感度による別経路があるだけでは飢餓を解消したと見なさない。

### v6追加分の受け入れ観点（実装時の検証案）

| 段階 | 確認すること |
|---|---|
| ① 記録・時間 | 同じ告白イベントでも発言と小声の返答で開示先が分かれる。内面deltaはfact化されない。停止・スリープを取り戻さず、保存再開でゲーム時刻と乱数系列を維持する |
| ① 相性 | 対称ルールで両向きの条件が一致しても同方向へ二重加算しない。該当なしは0、solo変化で再計算される |
| ② 認識 | 古い交際成立を後から知っても、新しい破局認識を巻き戻さない。同日中の順序を再現でき、未知を関係なしと混同しない |
| ② 反応 | 同factの聞き直し・保存中断・再実行で二重適用や欠落がない。両方を好きな観測者はall_matchesで異なる2割当を処理する |
| ② 描写・条件 | 特性に応じ祝福・落胆・無反応を分け、信頼を理由なく下げない。即時ログが抽選待ちにならず、後続イベントで元deltaを再適用しない |
| ③ 保護 | 反応も禁止・下限を守る。保護開始で対象カウンタだけリセットし、解除後に持ち越さない。非保護トラックには干渉しない |
| LLM／ChildEntity接続時 | 未知の事実をキャラ発話へ混ぜない。NSFW fact・イベント・プロンプトへのChildEntity混入を不変条件で拒否する |

表出保護の採否、LLM待機中の進行、人口運用、履歴期間は、上記の方向性をもって決定済みとは扱わない。
